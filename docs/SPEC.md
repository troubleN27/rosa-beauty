### 3.2 Защита от двойной записи

```sql
create extension if not exists btree_gist;

alter table bookings add constraint bookings_no_overlap
  exclude using gist (
    master_id with =,
    tstzrange(starts_at, ends_at, '[)') with &&
  ) where (status = 'confirmed');
```

При нарушении ограничения бот и админка показывают «Это время уже занято» и предлагают выбрать другое.

### 3.3 Стартовые данные (`seed.sql`)
- Настройки салона (адрес и контакты — вымышленные, но правдоподобные; часовой пояс `Europe/Moscow`, валюта USD).

- 5 мастеров с разной специализацией и графиками: 2 парикмахера-стилиста (стрижки, укладки, окрашивание), мастер ногтевого сервиса, бровист-лашмейкер, визажист-косметолог (макияж и уход за лицом). У одного выходные — понедельник и вторник, у другого — перерыв на обед, один работает только по выходным.
- Никаких тестовых записей и клиентов.

### 3.4 Доступ и подключение
- К базе обращаются только серверы: бот и серверная часть админки (Server Components, Server Actions, Route Handlers). Браузер никогда не подключается к БД напрямую, строка подключения не попадает в клиентский код.
- Схема описывается в `admin/src/db/schema.ts`, миграции генерируются `drizzle-kit generate` в `db/migrations/` и применяются `drizzle-kit migrate`. Расширение `btree_gist` и ограничение 3.2 Drizzle не умеет описать — они добавляются ручной миграцией (`drizzle-kit generate --custom`).
- Таблицы Better Auth (пользователи, сессии, аккаунты) создаются в той же базе и тоже входят в миграции.
- **Бот** подключается к Neon по **прямой (не pooled)** строке подключения с SSL. Если используется pooled-строка — отключить кэш подготовленных запросов asyncpg (`statement_cache_size=0`).
- **Админка** использует pooled-строку подключения через драйвер `@neondatabase/serverless`.
- Для разработки рекомендуется отдельная ветка Neon (`dev`), для работающей системы — `main`.

## 4. Telegram-бот

### 4.1 Режим работы
- Long polling (на Railway работает без домена и вебхука).
- Состояния диалога — FSM aiogram с `MemoryStorage`; при перезапуске незавершённый сценарий записи начинается заново, уже созданные записи не теряются.
- Язык клиента хранится в `clients.language`; все тексты через `t(key, lang, **params)` из `i18n/*.json`.

### 4.2 Клавиатуры
- Главное меню — reply-клавиатура (раздел 4.1 PRD).
- Шаги записи — inline-кнопки, у каждого шага есть «⬅️ Назад» и «✖️ Отмена».
- Календарь — inline-сетка на 14 дней от сегодня, недоступные дни — с пометкой и без действия.
- Время — inline-кнопки по 3–4 в ряд.
- Контакт — reply-кнопка `request_contact`.
- После каждого нажатия inline-кнопки — `callback.answer()`, сообщение шага редактируется (`edit_text`), а не отправляется заново, чтобы не засорять чат.

### 4.3 Callback data
Используются `CallbackData`-фабрики aiogram с короткими префиксами (`cat`, `svc`, `mst`, `day`, `slot`, `bk`), длина не более 64 байт.

### 4.4 Создание записи
1. В транзакции повторно проверить, что слот свободен.
2. Вставить запись со статусом `confirmed`, `source = 'bot'`, `price` = текущая цена услуги.
3. При ошибке исключающего ограничения — сообщение «Это время только что заняли» и возврат к выбору времени.
4. Отправить клиенту подтверждение, администратору — уведомление.

### 4.5 Отмена и перенос клиентом
- Разрешены, если `starts_at - now() >= cancel_deadline_hours`.
- Перенос — в одной транзакции: старая запись получает статус `cancelled` (`cancelled_by = 'client'`), создаётся новая. Если новый слот занят — старая запись остаётся без изменений.
- Каждое изменение статуса пишется в `booking_status_history`.

### 4.6 Планировщик (`scheduler.py`)

**Важно:** база Neon на бесплатном тарифе должна иметь возможность «засыпать» (она засыпает после 5 минут без запросов), иначе лимит вычислительных часов закончится до конца месяца. Поэтому **бот не опрашивает базу каждую минуту.** Напоминания планируются на точное время, а синхронизация с базой выполняется редко.

**Задачи на точное время (APScheduler, `DateTrigger`):**
- напоминание за 24 ч — `starts_at - 24 ч` (не ставится, если запись создана менее чем за 24 ч до визита);
- напоминание за 2 ч — `starts_at - 2 ч`;
- запрос отзыва — `ends_at + 2 ч` (ставится, когда запись получает статус `completed`).

ID задачи детерминированный: `remind24:<booking_id>`, `remind2:<booking_id>`, `review:<booking_id>` (`replace_existing=True`).

**Когда задачи ставятся и снимаются:**
- запись создана или перенесена в боте → поставить напоминания (для переноса — заменить);
- запись отменена в боте → снять задачи записи;
- при запуске бота и в **синхронизации раз в 30 минут** (`IntervalTrigger`) — выбрать из БД подтверждённые записи на ближайшие 26 часов и выполненные записи за последние 24 часа без запроса отзыва, и поставить недостающие задачи. Так подхватываются записи, созданные, перенесённые или завершённые в админке, а также всё, что было запланировано до перезапуска.

**Выполнение задачи:**
1. Перечитать запись из БД.
2. Отправить сообщение, только если условия всё ещё выполняются: для напоминаний — `status = 'confirmed'`, время визита не изменилось, соответствующий `reminder_*_sent_at is null`; для отзыва — `status = 'completed'`, `review_requested_at is null`, отзыва ещё нет. Иначе — ничего не делать.
3. После отправки проставить `reminder_24h_sent_at` / `reminder_2h_sent_at` / `review_requested_at`.

Флаги в БД гарантируют, что ничего не отправится дважды. Если время напоминания уже прошло (например, бот был выключен), но визит ещё не начался — напоминание за 2 ч отправляется сразу при синхронизации, напоминание за 24 ч пропускается, если до визита осталось меньше 2 ч. Учитываются настройки `reminders_enabled` / `reviews_enabled`.

Хранилище задач APScheduler — в памяти; источник правды — БД.

- Если клиент заблокировал бота — ошибка отправки логируется, работа продолжается.
- Логирование — стандартный `logging`, уровень из `.env`.

## 5. Алгоритм свободного времени

Реализуется в `bot/app/services/slots.py` и повторяется в `admin/src/lib/slots.ts` (одинаковая логика).

**Вход:** мастер, услуга (длительность), дата, настройки, текущее время.

1. Если дата в `time_off` мастера → слотов нет.
2. Взять `working_hours` на день недели → если нет, слотов нет.
3. Рабочий интервал `[start_time, end_time)` в часовом поясе салона, минус перерыв.
4. Вычесть интервалы подтверждённых записей мастера в этот день.
5. Получить свободные интервалы; внутри каждого генерировать начала слотов с шагом `slot_step_min`, выровненные по шагу от начала рабочего дня; слот подходит, если `start + duration <= конец свободного интервала`.
6. Отбросить слоты раньше `now + min_lead_time_min` и дальше `booking_horizon_days`.
7. Вернуть время в UTC и для показа — в часовом поясе салона.

**«Любой мастер»:** объединение слотов всех активных мастеров, выполняющих услугу; для каждого времени запоминается первый свободный мастер (порядок — `masters.sort`).

**Обязательные тесты (`test_slots.py`):**
- обычный день без записей;
- длинная услуга (240 минут) получает только слоты, где помещается целиком;
- запись в середине дня разбивает свободное время;
- перерыв на обед;
- услуга не помещается в конец дня;
- выходной по `time_off` и по отсутствию `working_hours`;
- минимальное время до записи (сегодняшний день);
- отменённые записи не блокируют время;
- «Любой мастер» выбирает свободного.

## 6. Веб-админка

### 6.1 Авторизация
- `/login` — email и пароль через Better Auth.
- Регистрация через интерфейс отключена; администратор создаётся командой `npm run create-admin -- --email … --password …`.
- Все страницы в `(dashboard)` защищены: без сессии — редирект на `/login`. Сессия дополнительно проверяется в каждой Server Action.
- Кнопка «Выйти» в меню.

### 6.2 Макет
- Боковое меню: Главная, Расписание, Записи, Услуги, Мастера, Клиенты, Отзывы, Настройки. На узких экранах — выезжающее меню.

- Цвета статусов: Подтверждена — синий, Выполнена — зелёный, Отменена — серый, Неявка — красный.

### 6.3 Страницы

|---|---|
| Главная | Карточки: записи сегодня, записи за неделю, выручка за неделю (сумма `price` выполненных), отмены и неявки, средняя оценка; список записей на сегодня; график записей по дням за 14 дней |
| Расписание | Переключатель День/Неделя и дата; сетка: колонки — мастера, строки — время с шагом 30 мин; записи блоками с услугой и клиентом; выходные и перерывы затемнены; клик → карточка записи (Sheet) |
| Записи | Таблица с фильтрами (период, мастер, статус, источник), сортировка, пагинация; кнопка «Новая запись» |
| Карточка записи | Данные записи, смена статуса, перенос (выбор слота через `slots.ts`), отмена, история статусов |
| Новая запись | Клиент (поиск по существующим или новый: имя + телефон), услуга, мастер, дата, свободный слот, комментарий |
| Услуги | Категории (вкладки) и услуги таблицей; создание и редактирование в диалоге; скрытие вместо удаления, если есть записи |
| Мастера | Список карточек; страница мастера: данные, фото (загрузка в Vercel Blob, JPG/PNG/WebP до 5 МБ, в БД хранится URL), услуги (чекбоксы), график по дням недели, выходные/отпуска |
| Клиенты | Таблица с поиском по имени и телефону: визиты, последний визит, отмены, неявки; карточка с историей |
| Отзывы | Таблица: дата, клиент, мастер, услуга, оценка (звёзды), комментарий; фильтр по оценке |
| Настройки | Форма со всеми полями таблицы `settings` |

### 6.4 Действия администратора и сообщения клиенту
Отмена или перенос записи администратором выполняется через Server Action, которая:
1. обновляет запись и пишет историю (`changed_by = 'admin'`, `cancelled_by = 'admin'`);
2. отправляет клиенту сообщение в бот на его языке через Telegram Bot API (`lib/telegram.ts`): «Ваша запись … отменена / перенесена на …». Если клиент заблокировал бота — показывается предупреждение, действие не откатывается.

Записи, созданные вручную (`source = 'admin'`), получают напоминания только если у клиента есть `telegram_id`. Если при ручной записи телефон совпадает с клиентом из бота — запись привязывается к нему.

## 7. Часовые пояса

- Все `timestamptz` хранятся в UTC.
- Отображение и расчёт рабочих часов — в `settings.timezone`.
- В тестах слотов — минимум один тест с часовым поясом, отличным от UTC.

## 8. Дизайн админки

- Светлая тема, тёплый нейтральный фон, акцентный цвет — пыльно-розовый `#C9707D` (кнопки, активный пункт меню, ссылки), тёмный текст `#1F1A1C`.

## 9. Безопасность

- Токен бота и строка подключения к БД — только в переменных окружения.
- Все Server Actions админки проверяют сессию пользователя.
- Пользовательский ввод валидируется (zod в админке, проверки в хендлерах бота).
- В сообщениях Telegram с HTML-разметкой пользовательский текст экранируется.

## 10. Деплой (выполняет владелец проекта, Claude готовит инструкции)

- **Neon:** создать проект (регион ближе к серверу бота) → получить прямую и pooled строки подключения → применить миграции (`npm run db:migrate`) и стартовые данные (`npm run db:seed`) → создать администратора (`npm run create-admin`).
- **Бот → Railway:** деплой из GitHub, Root Directory `bot`, Railway сам собирает Python-проект по `pyproject.toml` (Docker не используется), команда запуска `python -m app.main` задаётся в настройках сервиса Railway; переменные из 4.9 (`DATABASE_URL` — прямая строка Neon в формате `postgresql+asyncpg://…`, SSL обязателен).
- **Админка → Vercel:** Root Directory `admin`, переменные из 6.5; подключить хранилище Vercel Blob к проекту.
- В настройках вычислений Neon установить размер compute **0.25 CU** (минимальный) и оставить автоматическое «засыпание» включённым — так бесплатного лимита хватает на весь месяц.
